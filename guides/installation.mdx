The Flux Operator is a statically compiled Go binary with no external dependencies, designed to run on Linux nodes (AMD64 or ARM64) across all major Kubernetes distributions. It can be installed through several methods — Helm, Terraform, Operator Lifecycle Manager (OLM), the `flux-operator` CLI, or `kubectl` — and is recommended to be deployed in a dedicated namespace such as `flux-system`.

## Install Methods

<Tabs>
  <Tab title="Helm">
    Helm is the recommended installation method for production environments. The Flux Operator Helm chart is published to GitHub Container Registry as an OCI artifact.

    ```shell
    helm install flux-operator oci://ghcr.io/controlplaneio-fluxcd/charts/flux-operator \
      --namespace flux-system \
      --create-namespace
    ```

    ### Helm Chart Values

    The Helm chart exposes a rich set of values to customize the operator deployment. You can pass operator configuration flags via `extraArgs` and set environment variables for OLM-style deployments:

    ```yaml
    # values.yaml
    extraArgs:
      - --log-level=info
      - --concurrent=10
      - --reporting-interval=5m
      - --watch-configs-label-selector=reconcile.fluxcd.io/watch=Enabled

    resources:
      limits:
        cpu: 1000m
        memory: 512Mi
      requests:
        cpu: 100m
        memory: 64Mi

    tolerations: []
    affinity: {}
    ```

    Pass a custom values file at install time:

    ```shell
    helm install flux-operator oci://ghcr.io/controlplaneio-fluxcd/charts/flux-operator \
      --namespace flux-system \
      --create-namespace \
      --values values.yaml
    ```

    <Tip>
      To pin to a specific chart version, append `--version <semver>` to the install command. Automating upgrades via a Flux `HelmRelease` and `OCIRepository` is the recommended approach for production — see the [upgrade section](#upgrade) below.
    </Tip>
  </Tab>

  <Tab title="Terraform">
    The Flux Operator can be bootstrapped with Terraform using the official `flux-operator-bootstrap` module:

    ```hcl
    module "flux_operator_bootstrap" {
      source  = "controlplaneio-fluxcd/flux-operator-bootstrap/kubernetes"

      revision = var.bootstrap_revision

      gitops_resources = {
        instance_yaml = file("${path.root}/clusters/staging/flux-system/flux-instance.yaml")
      }
    }
    ```

    The module installs the operator and applies the `FluxInstance` manifest in a single step. For a full working example, see the [terraform example](https://github.com/controlplaneio-fluxcd/flux-operator/tree/main/config/terraform) in the project repository.
  </Tab>

  <Tab title="OLM / OperatorHub">
    On OpenShift and OKD clusters, the Flux Operator can be installed through Operator Lifecycle Manager (OLM) from [operatorhub.io/operator/flux-operator](https://operatorhub.io/operator/flux-operator). It is also available in the [RedHat community operators production catalog](https://github.com/redhat-openshift-ecosystem/community-operators-prod).

    Create a `Subscription` manifest to install the operator:

    ```yaml
    apiVersion: operators.coreos.com/v1alpha1
    kind: Subscription
    metadata:
      name: flux-operator
      namespace: flux-system
    spec:
      channel: stable
      name: flux-operator
      source: operatorhubio-catalog
      sourceNamespace: olm
      config:
        env:
          - name: DEFAULT_SERVICE_ACCOUNT
            value: "flux-operator"
          - name: REPORTING_INTERVAL
            value: "30s"
        affinity:
          nodeAffinity:
            requiredDuringSchedulingIgnoredDuringExecution:
              nodeSelectorTerms:
                - matchExpressions:
                    - key: role
                      operator: In
                      values:
                        - flux
        tolerations:
          - effect: NoSchedule
            key: role
            operator: Equal
            value: flux
    ```

    <Note>
      Flux Operator supports several environment variables specifically for OLM installations: `DEFAULT_SERVICE_ACCOUNT`, `DEFAULT_WORKLOAD_IDENTITY_SERVICE_ACCOUNT`, `REPORTING_INTERVAL`, `OVERRIDE_MANAGERS`, `WEB_SERVER_PORT`, and `WEB_CONFIG_SECRET_NAME`. These are set in the `Subscription` manifest under `config.env`.
    </Note>
  </Tab>

  <Tab title="Flux Operator CLI">
    The `flux-operator` CLI provides a single command to bootstrap a cluster with both the operator and a Flux instance in one step.

    First, install the CLI with Homebrew:

    ```shell
    brew install controlplaneio-fluxcd/tap/flux-operator
    ```

    Then install the operator and Flux instance from a configuration file:

    ```shell
    flux-operator install -f flux-instance.yaml
    ```

    The install command:
    1. Downloads the Flux Operator distribution artifact from `oci://ghcr.io/controlplaneio-fluxcd/flux-operator-manifests`
    2. Installs the operator in the `flux-system` namespace and waits for readiness
    3. Applies the Flux instance according to the provided configuration
    4. Optionally configures pull secrets and sync source credentials
    5. Optionally enables automatic operator updates from the distribution artifact

    <Note>
      The CLI install command is intended for development and testing. For production environments, use Helm or Terraform.
    </Note>
  </Tab>

  <Tab title="kubectl">
    For quick development or testing setups, apply the release manifest directly with `kubectl`:

    ```shell
    kubectl apply -f https://github.com/controlplaneio-fluxcd/flux-operator/releases/latest/download/install.yaml
    ```

    <Warning>
      This method is intended for development and testing only. In production environments, use Helm or Terraform so that upgrades, rollbacks, and configuration changes are managed declaratively.
    </Warning>
  </Tab>
</Tabs>

## Upgrade

The recommended way to upgrade the Flux Operator is via GitOps — managing the operator's installation with a Flux `HelmRelease` backed by an `OCIRepository` source. This allows upgrades to be triggered automatically when a new Helm chart version is published without any manual intervention.

A complete example using a `ResourceSet` to manage both the `OCIRepository` and `HelmRelease` is provided in the [migration guide](/guides/migration#automating-flux-operator-upgrades).

## Uninstall

The safest way to remove the Flux Operator and Flux controllers is with the CLI's `uninstall` command:

```shell
flux-operator -n flux-system uninstall --keep-namespace
```

<Steps>
  <Step title="What uninstall does">
    The command executes the following steps in order:
    1. Deletes the cluster role bindings of the Flux Operator and Flux controllers
    2. Deletes the deployments of the Flux Operator and Flux controllers
    3. Removes finalizers from Flux Operator and Flux custom resources
    4. Deletes the CustomResourceDefinitions of the Flux Operator and Flux
    5. Deletes the namespace (unless `--keep-namespace` is passed)
  </Step>
  <Step title="What uninstall preserves">
    The `uninstall` command does **not** delete any Kubernetes objects or Helm releases that were previously reconciled by Flux. It is safe to run this command and re-install the operator later to resume managing the existing resources.
  </Step>
</Steps>

## Operator Configuration Reference

The Flux Operator supports a comprehensive set of flags and environment variables. Flags are passed to the operator container via the Helm chart's `extraArgs` values key.

| Flag | Default | Description |
|------|---------|-------------|
| `--concurrent` | `10` | The number of concurrent resource reconciles |
| `--default-service-account` | | Default service account used for impersonation |
| `--default-workload-identity-service-account` | | Default service account to use for workload identity when not specified in resources |
| `--enable-leader-election` | `true` | Enable leader election for controller manager |
| `--health-addr` | `:8081` | The address the health endpoint binds to |
| `--interval-jitter-percentage` | `5` | Percentage of jitter to apply to interval durations |
| `--leader-election-lease-duration` | `35s` | Interval at which non-leader candidates will wait to force acquire leadership |
| `--leader-election-release-on-cancel` | `true` | Defines if the leader should step down voluntarily on controller manager shutdown |
| `--leader-election-renew-deadline` | `30s` | Duration that the leading controller manager will retry refreshing leadership before giving up |
| `--leader-election-retry-period` | `5s` | Duration the LeaderElector clients should wait between tries of actions |
| `--log-encoding` | `json` | Log encoding format: `json` or `console` |
| `--log-level` | `info` | Log verbosity level: `trace`, `debug`, `info`, `error` |
| `--max-retry-delay` | `15m` | The maximum amount of time for which an object being reconciled will have to wait before a retry |
| `--metrics-addr` | `:8080` | The address the metrics endpoint binds to |
| `--min-retry-delay` | `750ms` | The minimum amount of time for which an object being reconciled will have to wait before a retry |
| `--override-manager` | | Field manager disallowed to perform changes on managed resources (repeatable) |
| `--reporting-interval` | `5m` | The interval at which the Flux report is computed |
| `--requeue-dependency` | `5s` | The interval at which failing dependencies are reevaluated |
| `--storage-path` | `/data` | The local storage path |
| `--token-cache-max-duration` | `1h` | The maximum duration a token is cached |
| `--token-cache-max-size` | `100` | The maximum size of the cache in number of tokens |
| `--watch-configs-label-selector` | `reconcile.fluxcd.io/watch=Enabled` | Watch for ConfigMaps and Secrets with matching labels |
| `--web-config` | | The path to the configuration file for the web server |
| `--web-config-secret-name` | | The name of the Kubernetes Secret containing the web server configuration |
| `--web-server-only` | `false` | Run only the web server without starting the controllers |
| `--web-server-port` | `9080` | The port for the web server to listen on (`0` to disable) |
